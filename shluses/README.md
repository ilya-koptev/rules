# shluses

Правило `wb-rules` для судоходного шлюза: двое ворот, камера, налив и слив.
Один и тот же файл на всех шлюзах — адреса модулей везде одинаковые.

Главное правило: **обе ворота никогда не открыты одновременно**, налив и слив — только
при закрытых обоих воротах.

## Модули

Все на `/dev/ttyRS485-2`, 115200 8N2. Адреса одинаковые на всех шлюзах:

| Адрес | Модуль | Что делает |
|---|---|---|
| 10 | WB-UPS v3 | резерв питания |
| 11 | WB-MAO4 | верхние ворота |
| 12 | WB-MAO4 | нижние ворота |
| 13 | WB-MCM8 | импульсы моторов: вход 1 — верхние, вход 2 — нижние |
| 14 | WB-MAI6 | IN1/IN2 — токи моторов (может не быть), IN5 — датчик уровня 4–20 мА |
| 15 | WB-MRM2-mini | K1 — налив камеры, K2 — слив |

### Как работают ворота

У каждого MAO4: выход 1 — мотор, выход 2 — направление (идёт на вход Z/F драйвера),
0 — открывать, 1 — закрывать. Концевики — герконы на вход 1 («открыто») и вход 2
(«закрыто»). Входы в режиме «Выключатель с фиксацией», с локальными действиями:

| Событие | Вход 1 «открыто» | Вход 2 «закрыто» |
|---|---|---|
| геркон замкнулся | выход 2 → включить | выход 2 → выключить |
| геркон разомкнулся | выход 1 → выключить | выход 1 → выключить |

Ворота наезжают на магнит, мотор разворачивается, ворота отскакивают назад, сходят с
магнита — и мотор гаснет. Ворота стоят у края магнита с направлением на обратный ход,
поэтому **чтобы двинуть ворота, достаточно включить выход 1**. Останавливает модуль сам,
даже если правило не работает.

## Установка

```bash
scp shluses.js add-dashboards.py root@192.168.хх.хх:/root/
ssh root@192.168.хх.хх 'cp /root/shluses.js /etc/wb-rules/ && python3 /root/add-dashboards.py'
```

`add-dashboards.py` дописывает в веб-интерфейс панели «Шлюз» (для пользователя, она же
панель по умолчанию) и «Шлюз — наладка». Бэкап конфига — в `/root/`, чужие панели не
трогает, повторный запуск заменяет свои.

После старта правила (и после каждой перезагрузки контроллера) положение ворот неизвестно,
поэтому обе ворота сначала едут закрываться. Уже закрытые наезжают на магнит, отскакивают
и встают — 1–2 секунды.

## MQTT

Прочитать — `/devices/<устройство>/controls/<контрол>`, команда — тот же топик с `/on`.

### `shluz` — для пользователя и внешней системы

| Контрол | Доступ | Назначение |
|---|---|---|
| `open_upstream` | кнопка | открыть верхний бьеф: закрыть ворота → налить камеру → открыть верхние |
| `open_downstream` | кнопка | открыть нижний бьеф: закрыть ворота → слить камеру → открыть нижние |
| `close_gates` | кнопка | закрыть обе ворота |
| `stop` | кнопка | остановить всё: моторы, клапаны, цикл |
| `reset` | кнопка | сбросить ошибку (ворота не двигает) |
| `init` | кнопка | инициализация: забыть положение ворот, сбросить ошибки, закрыть обе ворота до концевика |
| `status` | чт. | `init` — инициализация, `busy` — идёт цикл, `closed`, `upstream_open`, `downstream_open`, `unknown`, `error` |
| `step` | чт. | что сейчас делает (коды ниже) |
| `error` | чт. | причина ошибки, текст латиницей, например `upper gate: no limit switch within 30 s` |
| `upper_gate`, `lower_gate` | чт. | `closed` / `open` / `opening` / `closing` / `stopped` / `unknown` / `error` |
| `chamber` | чт. | заполнение камеры, `N%`: 0 % — 70 мм, 100 % — 140 мм; `no_sensor` — нет показаний датчика |

Налив и слив идут до порогов уровня «залито» / «слито», заданных на панели наладки; не дошли
за отведённое время — клапан закрывается, ошибка, ворота не открываются.

Пока ворота едут, в `step` каждую секунду пишется, насколько они открыты: на концевике 0 или
100 %, между концевиками — по импульсам мотора.

Коды `step`:

| Код | Что делает |
|---|---|
| `closing_upper N%`, `closing_lower N%` | закрывает ворота (обе сразу — через пробел); при инициализации то же, `status` = `init` |
| `filling` / `draining` | наливает / сливает камеру через клапан |
| `crack_upper N%` / `crack_lower N%` | через клапан не идёт — приоткрывает верхние / нижние ворота |
| `filling_through_gate` / `draining_through_gate` | наливает / сливает через приоткрытые ворота |
| `opening_upper N%` / `opening_lower N%` | открывает верхние / нижние ворота |
| `stopped` | остановлено кнопкой «Стоп» |
| `interrupted_manual` | цикл прерван ручной командой с панели наладки |
| `on_battery` / `ethernet_lost` | сбой: закрывает ворота |
| пусто | ничего не делает |

Новая команда посреди цикла прерывает его и начинает свою. При ошибке команды не
принимаются, пока её не сбросят.

### Примеры

`192.168.хх.хх` — адрес контроллера шлюза. Брокер Wiren Board по умолчанию пускает без пароля,
команды можно слать с любой машины в той же сети.

Смотреть всё, что отдаёт шлюз:

```bash
mosquitto_sub -h 192.168.хх.хх -v -t '/devices/shluz/controls/+'
```

Только состояние и шаг:

```bash
mosquitto_sub -h 192.168.хх.хх -v -t /devices/shluz/controls/status -t /devices/shluz/controls/step
```

Прочитать текущее состояние один раз:

```bash
mosquitto_sub -h 192.168.хх.хх -C 1 -t /devices/shluz/controls/status
```

Команды:

```bash
mosquitto_pub -h 192.168.хх.хх -t /devices/shluz/controls/open_upstream/on   -m 1
mosquitto_pub -h 192.168.хх.хх -t /devices/shluz/controls/open_downstream/on -m 1
mosquitto_pub -h 192.168.хх.хх -t /devices/shluz/controls/close_gates/on     -m 1
mosquitto_pub -h 192.168.хх.хх -t /devices/shluz/controls/stop/on            -m 1
mosquitto_pub -h 192.168.хх.хх -t /devices/shluz/controls/reset/on           -m 1
mosquitto_pub -h 192.168.хх.хх -t /devices/shluz/controls/init/on            -m 1
```

Как выглядит цикл «закрыть ворота» в подписке на `status` и `step` (ворота уже закрыты):

```
/devices/shluz/controls/status closed
/devices/shluz/controls/step closing
/devices/shluz/controls/status busy
/devices/shluz/controls/step
/devices/shluz/controls/status closed
```

Дождаться конца цикла в скрипте:

```bash
H=192.168.хх.хх
mosquitto_pub -h $H -t /devices/shluz/controls/open_upstream/on -m 1
sleep 2
until s=$(mosquitto_sub -h $H -C 1 -t /devices/shluz/controls/status); [ "$s" != busy ]; do sleep 2; done
echo "готово: $s"     # upstream_open — успех, error — смотреть /devices/shluz/controls/error
```

## Modbus TCP

**Это временное решение, опытное.** Основной способ — MQTT выше: там полные тексты,
события приходят сами, ничего не надо опрашивать. Modbus сделан для внешней системы,
которая MQTT не умеет. Карта регистров может поменяться — перед тем как закладываться
на неё, сверьтесь с этим разделом.

Работает через штатный `wb-mqtt-mbgate` — службу Wiren Board, которая отдаёт выбранные
MQTT-топики как Modbus TCP, порт 502. Наружу видно **только то, что перечислено в
`/etc/wb-mqtt-mbgate.conf` с `"enabled": true`**, всё остальное недоступно физически.

### Как настроить

Настраивается на каждом шлюзе отдельно, вручную, по этому описанию. Готового скрипта
нет намеренно: шлюзов немного, а правка затрагивает то, что отдаётся наружу.

**Через веб-интерфейс настраивать не надо.** Страница «Modbus TCP gateway» раздаёт
каждой строке случайные `unitId` и `address` — тогда на каждом шлюзе получится своя
карта, и таблица ниже станет неверной. Адреса задаются руками, одинаковые везде.

Порядок:

1. Сделать бэкап: `cp /etc/wb-mqtt-mbgate.conf /mnt/data/etc/wb-mqtt-mbgate.conf.bak-<дата>`.
2. В `"modbus"` должно быть `{"host": "*", "port": 502}`.
3. **Всем** строкам в `"registers"` поставить `"enabled": false`. Это важнее остального:
   в заводском конфиге обычно включены прямые каналы WB-MAO4 — через них снаружи
   крутится мотор мимо правила и всех его защит.
4. Добавить двенадцать строк устройства `shluz` по таблицам ниже, все на `unitId` 1.
   Кнопки — в массив `"coils"`:

   ```json
   { "enabled": true, "topic": "shluz/open_upstream", "unitId": 1, "address": 0 }
   ```

   Тексты — в массив `"inputs"`, каждый занимает 24 регистра подряд:

   ```json
   { "enabled": true, "topic": "shluz/status", "unitId": 1, "address": 0,
     "format": "varchar", "size": 24, "scale": 1,
     "byteswap": false, "wordswap": false }
   ```

5. Убедиться, что адреса 0–5 в `coils` и 0–143 в `inputs` не заняты другими строками
   (даже выключенными — выключенную легко включить обратно и получить наложение).
6. Запустить: `systemctl enable --now wb-mqtt-mbgate`, проверить
   `ss -lntp | grep :502` и чтение из таблицы ниже.

Фаервол на контроллере обычно пустой, отдельно открывать 502 не требуется.

### Карта регистров

Всё на **unit ID 1**.

Кнопки — coils, запись `1` = нажатие (функция 5, значение `0xFF00`):

| Адрес | Топик | Что делает |
|---|---|---|
| 0 | `shluz/open_upstream` | открыть верхний бьеф |
| 1 | `shluz/open_downstream` | открыть нижний бьеф |
| 2 | `shluz/close_gates` | закрыть обе ворота |
| 3 | `shluz/stop` | стоп |
| 4 | `shluz/reset` | сбросить ошибку |
| 5 | `shluz/init` | инициализация |

Состояние — input registers (функция 4), формат `varchar`, по 24 регистра на поле:

| Адрес | Топик | Что |
|---|---|---|
| 0 | `shluz/status` | состояние |
| 24 | `shluz/step` | что делает |
| 48 | `shluz/error` | ошибка |
| 72 | `shluz/upper_gate` | верхние ворота |
| 96 | `shluz/lower_gate` | нижние ворота |
| 120 | `shluz/chamber` | заполнение камеры |

Значения — те же строки, что и в MQTT, их список в разделе выше.

### Повадки, которые надо знать

Проверено на `wb-mqtt-mbgate` 1.12.0:

- **`varchar` кладёт по одному символу в регистр**, старший байт нулевой. Строка
  `open` приходит как `00 6F 00 70 00 65 00 6E`. Значит 24 регистра = 24 символа,
  длиннее — обрежется.
- **Пустое значение — не пустая строка, а отказ**: чтение отвечает исключением 11
  (`GATEWAY TARGET DEVICE FAILED TO RESPOND`). Так ведут себя `step` и `error`, когда
  шлюз ничего не делает и ошибок нет. Это нормальное состояние, обрабатывайте как «пусто».
- **Кнопки не читаются** — у `pushbutton` нет состояния, чтение coils даёт то же
  исключение 11. Писать можно, читать нечего.
- **Чужое не отвечает вовсе.** Выключенный топик или чужой unit ID не дают исключения —
  ответа нет совсем, клиент получит таймаут. Выход за край своего списка
  (coil 6, input 144) даёт честное исключение 2 `ILLEGAL DATA ADDRESS`.

### Примеры

Без библиотек, на голом сокете:

```python
import socket, struct

HOST = "192.168.хх.хх"

def rq(s, unit, func, payload):
    s.sendall(struct.pack(">HHHBB", 1, 0, len(payload) + 2, unit, func) + payload)
    head = s.recv(6)
    data = s.recv(struct.unpack(">HHH", head)[2])
    if data[1] & 0x80:
        raise ValueError("исключение %d" % data[2])
    return data[2:]

s = socket.create_connection((HOST, 502), timeout=10)

# прочитать состояние: input registers 0..23
raw = rq(s, 1, 4, struct.pack(">HH", 0, 24))[1:]
print(bytes(raw[1::2]).decode().rstrip("\x00"))       # upstream_open

# нажать «открыть верхний бьеф»: coil 0 := 1
rq(s, 1, 5, struct.pack(">HH", 0, 0xFF00))
```

Тем же `modpoll`:

```bash
modpoll -m tcp -a 1 -t 3 -r 1  -c 24 192.168.хх.хх     # status, регистры 1..24
modpoll -m tcp -a 1 -t 0 -r 1  192.168.хх.хх 1         # нажать open_upstream
```

(`modpoll` нумерует регистры с единицы, поэтому адрес 0 — это `-r 1`.)

### Одновременная работа по MQTT и по Modbus

Это один и тот же шлюз. Modbus ничего не делает сам: `wb-mqtt-mbgate` просто публикует
в тот же MQTT-топик, что и `mosquitto_pub`. Поэтому на уровне регистров конфликта нет —
конфликт бывает на уровне команд, и он ровно такой же, как у двух людей у одной панели.

Что из этого следует:

- **Команды не складываются, последняя побеждает.** Новая команда посреди цикла
  прерывает его и начинает свою (см. раздел MQTT). Если внешняя система послала
  «открыть верхний бьеф», а в это время кто-то нажал «закрыть ворота» — поедет закрытие,
  и внешняя система об этом не узнает, пока не посмотрит `status` и `step`.
- **Держите одного хозяина за раз.** Либо шлюзом правит внешняя система, либо человек
  с панели. Переключение — осознанное действие, а не «оба шлют, когда хочется».
- **Перед командой смотрите `status`.** `busy` — идёт цикл, его чужая команда прервёт.
  `error` — команды вообще не принимаются, пока ошибку не сбросят.
- **После команды дождитесь конца цикла** по `status`, как в примере со скриптом выше, и
  только потом шлите следующую. Слать команды чаще, чем шлюз успевает отрабатывать, —
  верный способ получить не тот бьеф.
- **Защиты одинаковы для всех.** Блокировки, таймауты и закрытие по сбою питания и сети
  работают независимо от того, откуда пришла команда: они внутри правила, а оба пути
  ведут в него.

Чего Modbus не даёт и не должен: настроек наладки. Пороги, таймауты, калибровка,
ручное управление воротами и клапанами остаются только в веб-интерфейсе.

## Настройки

Настройки — пороги уровня, таймауты, калибровка датчика, реле заливочных насосов, ручное
управление воротами и клапанами — только в веб-интерфейсе контроллера, панель «Шлюз — наладка».
В API они не входят: внешняя система работает только с устройством `shluz`.

Клапан с заливочным насосом может питаться через реле на другом контроллере, включённое
последовательно с реле шлюза; правило включает его само вместе со своим. На время слива
выключается наполнение русла, чтобы потоки не мешали друг другу.

## Защиты

- **Блокировка** — кто бы ни включил мотор (правило, кнопка в веб-интерфейсе, внешняя
  система): ворота, поехавшие на открытие, останавливаются, если другие не подтверждены
  закрытыми или открыт любой клапан. Отскок от магнита блокировкой не считается.
- **Клапаны** — открываются только при закрытых обоих воротах; ворота перестали быть
  закрытыми — клапаны закрываются.
- **Таймаут хода** — не доехали до концевика — стоп и ошибка.
- **Ток мотора** — если задан порог и MAI6 отдаёт ток. Нет MAI6 — защита молчит.
- **Сбой питания или сети** — работа от батареи или пропал Ethernet: клапаны и обе
  ворота закрываются.

## Не проверено

- Пороги уровня и калибровка датчика по умолчанию — не мерились, на каждом шлюзе задаются на
  панели наладки.
- Реакция на пропажу Ethernet и на работу от батареи живьём не проверялась.
